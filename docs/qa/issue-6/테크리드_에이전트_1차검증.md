## Notification Type 정책

| type | 화면 표시 | target.type | 이동 화면 |
|---|---|---|---|
| `CHAT` | 채팅 | `CHAT` | 해당 방 채팅 화면 |
| `LETTER` | 편지 | `LETTER` | 해당 방 편지 화면 |
| `MEMORY` | 추억 | `MEMORY` | 해당 방 추억 게시판 |
| `MISSION_APPROVAL_REQUEST` | 미션 | `MISSION` | 해당 방 미션 인증 화면 |
| `MISSION_PROGRESS` | 미션 | `MISSION` | 해당 방 미션 인증 화면 |

target url은 프론트 라우터가 아직 URL routing 기반이 아니므로 서버가 제공하되, 프론트는 `target.type`과 `roomId` 기준으로 현재 placeholder 화면으로 이동한다.

## DB / QueryDSL 기준

현재 `V3__create_notification_and_settings_tables.sql`의 `notifications` 스키마는 `docs/dev-spec/DEV-002-domain-db-model.md`와 일부 차이가 있다.

현재 스키마:

- `title`
- `message`
- `target_type`
- `target_id`
- `occurred_date`
- `created_at`

구현 기준:

- 기존 컬럼은 rename/drop 하지 않는다.
- `actor_member_id`는 화면에서 "누가"를 표시하기 위해 신규 migration으로 추가한다.
- 응답 `summary`는 현재 DB의 `message`를 매핑한다.
- 응답 `occurredAt`은 현재 DB의 `created_at`을 매핑한다.
- `read`는 `read_at is not null`로 판단한다.
- room/actor/member 조인은 QueryDSL을 우선 사용한다.
- 단건 읽음 처리는 JPA entity 조회 후 소유자 검증과 상태 변경으로 처리한다.

## Service Layer 기준

메인 서비스 레이어는 흐름이 보여야 한다.

예:

```kotlin
fun readNotification(memberId: Long, notificationId: Long): NotificationReadResponse {
    val member = currentMemberResolver.resolve(memberId)
    val notification = notificationRepository.findOwnedNotification(notificationId, member.id)
    notification.markAsRead(clock.now())
    notificationRepository.save(notification)
    return NotificationReadResponse(read = true)
}
```

Repository 등 서비스가 호출하는 외부 책임 클래스의 공개 메서드에는 한국어 한 줄 주석을 둔다.

실패 로그는 언제/어디서/왜가 남게 한다.

```kotlin
logError(e) {
    "[알림 읽음 처리] 실패. " +
        "who=memberId:$memberId, " +
        "what=NotificationService.readNotification, " +
        "requestData=notificationId:$notificationId, " +
        "reason=${e.message}"
}
```

## curl 테스트 계획

공통:

BASE_URL=http://localhost:8080/api

### GET /api/notifications/latest

| 케이스 | 명령 | 기대 결과 |
|---|---|---|
| 최신 알림 조회 | `curl -i -H "X-Member-Id: 1" "$BASE_URL/notifications/latest"` | HTTP 200, `items` 최대 3개 |
| limit 3 검증 | 위 명령 후 `items.length` 확인 | seed 알림이 4개 이상이어도 3개만 반환 |
| 최신순 정렬 | 위 응답의 `occurredAt` 순서 확인 | 내림차순 |
| 타입 구분 | 위 응답의 `type` 확인 | CHAT/LETTER/MEMORY/MISSION 계열 포함 |
| target url shape | 위 응답의 `target.url` 확인 | `/rooms/{roomId}/...` 형태 |
| header 누락 | `curl -i "$BASE_URL/notifications/latest"` | HTTP 401 |
| 없는 member | `curl -i -H "X-Member-Id: 99999" "$BASE_URL/notifications/latest"` | HTTP 401 또는 404 계열 한국어 오류 |

### GET /api/notifications

| 케이스 | 명령 | 기대 결과 |
|---|---|---|
| 기본 목록 | `curl -i -H "X-Member-Id: 1" "$BASE_URL/notifications"` | HTTP 200, 기본 size 적용 |
| paging size | `curl -i -H "X-Member-Id: 1" "$BASE_URL/notifications?page=0&size=2"` | HTTP 200, `items` 최대 2개 |
| 두 번째 page | `curl -i -H "X-Member-Id: 1" "$BASE_URL/notifications?page=1&size=2"` | HTTP 200, 다음 목록 |
| 음수 page | `curl -i -H "X-Member-Id: 1" "$BASE_URL/notifications?page=-1&size=20"` | HTTP 400 |
| size 초과 | `curl -i -H "X-Member-Id: 1" "$BASE_URL/notifications?page=0&size=101"` | HTTP 400 |

### POST /api/notifications/{notificationId}/read

| 케이스 | 명령 | 기대 결과 |
|---|---|---|
| 읽음 처리 성공 | `curl -i -X POST -H "X-Member-Id: 1" "$BASE_URL/notifications/1/read"` | HTTP 200, `read=true` |
| idempotent read | 같은 명령 재호출 | HTTP 200, `read=true` |
| 존재하지 않는 id | `curl -i -X POST -H "X-Member-Id: 1" "$BASE_URL/notifications/99999/read"` | HTTP 404 |
| 타인 알림 차단 | `curl -i -X POST -H "X-Member-Id: 2" "$BASE_URL/notifications/1/read"` | HTTP 404 또는 403 |
| header 누락 | `curl -i -X POST "$BASE_URL/notifications/1/read"` | HTTP 401 |
| id 형식 오류 | `curl -i -X POST -H "X-Member-Id: 1" "$BASE_URL/notifications/abc/read"` | HTTP 400 |

- target 상세 화면은 아직 placeholder이므로 실제 상세 위치 focus는 query string 저장보다 room 선택 + feature view 이동까지만 구현한다.
