## 1. 구현 범위

Issue #6은 메인 화면의 최신 알림 카드, 전체 알림 모달, 알림 읽음 처리, 알림 클릭 후 방/기능 이동 정책을 구현한다.

포함:

- 최신 알림 3개 조회
- 전체 알림 목록 paging 조회
- 알림 읽음 처리
- 채팅/편지/추억/미션 알림 구분 표시
- 알림 클릭 시 해당 방 선택 후 대상 기능 화면으로 이동

제외:

- push notification
- 실시간 알림
- 채팅/편지/추억/미션 상세 CRUD 신규 구현
- 삭제된 target 복구 UI

## 2. 구현 대상 API 목록과 역할

| API | 역할 | 화면 연결 |
| --- | --- | --- |
| `GET /api/notifications/latest` | 메인 화면 우측 상단 최신 알림을 최신순 최대 3개 반환 | 메인 최신 알림 카드 |
| `GET /api/notifications?page=0&size=20` | 최신 알림 전체 보기 모달의 목록을 paging으로 반환 | 전체 알림 모달 |
| `POST /api/notifications/{notificationId}/read` | 알림을 읽음 처리 | 알림 카드/모달 항목 클릭 직후 |

공통 규칙:

- 로컬 MVP 인증은 `X-Member-Id` header를 사용한다.
- 모든 조회/읽음 처리는 `receiver_member_id = X-Member-Id` 기준으로 제한한다.
- 응답은 화면에서 바로 쓸 수 있는 view model 형태로 반환한다.
- 알림 target이 삭제되었거나 접근 불가능하면 프론트가 삭제 안내 상태를 보여줄 수 있게 target 상태를 null-safe로 처리한다.

## 3. Response Shape 기준

`GET /api/notifications/latest`와 `GET /api/notifications`의 item shape는 동일하게 맞춘다.

```json
{
  "items": [
    {
      "id": 1,
      "type": "MISSION_APPROVAL_REQUEST",
      "roomId": 1,
      "roomName": "우리 둘의 100일",
      "actorName": "민지",
      "summary": "미션 인증 동의를 기다립니다.",
      "occurredAt": "2026-07-17T22:10:00+09:00",
      "read": false,
      "target": {
        "type": "MISSION",
        "id": 1,
        "url": "/rooms/1/missions?focusSubmissionId=1"
      }
    }
  ]
}
```

전체 목록은 common page response를 따른다.

```json
{
  "items": [],
  "page": 0,
  "size": 20,
  "hasNext": false
}
```

## 4. Notification Type / Target Type 정책

`notification_type`은 DB 모델의 enum 값을 기준으로 한다.

| notification.type | 화면 표시 | target.type | target.url shape | 이동 정책 |
| --- | --- | --- | --- | --- |
| `CHAT` | 채팅 | `CHAT` | `/rooms/{roomId}/chat?focusMessageId={targetId}` | 해당 방 선택 후 채팅 화면으로 이동 |
| `LETTER` | 편지 | `LETTER` | `/rooms/{roomId}/letters/{targetId}` | 해당 방 선택 후 편지 상세 또는 받은 편지함으로 이동 |
| `MEMORY` | 추억 | `MEMORY` | `/rooms/{roomId}/memories/{targetId}` | 해당 방 선택 후 추억 게시글 상세로 이동 |
| `MISSION_APPROVAL_REQUEST` | 미션 | `MISSION` | `/rooms/{roomId}/missions?focusSubmissionId={targetId}` | 해당 방 선택 후 미션 인증 승인 대기 위치로 이동 |
| `MISSION_APPROVAL_RATE` | 미션 | `MISSION` | `/rooms/{roomId}/missions?focusSubmissionId={targetId}` | 해당 방 선택 후 미션 인증 상세 또는 진행률 위치로 이동 |

프론트 이동 기준:

- 현재 router가 상세 URL을 완전히 지원하지 않더라도 서버는 위 URL shape를 내려준다.
- 프론트는 최소한 `roomId`로 사이드바의 선택 방을 바꾸고, `target.type`에 맞는 기능 화면으로 이동해야 한다.
- 상세 focus가 아직 구현되지 않았으면 query string은 보존하되 해당 기능의 기본 화면으로 이동한다.
- 알림 클릭 후 read API가 성공하면 해당 알림은 읽음 스타일로 변경한다.

## 5. QueryDSL/JPA 사용 기준

### QueryDSL 사용

목록 조회는 QueryDSL 기반 projection을 우선 사용한다.

적용 대상:

- `GET /api/notifications/latest`
- `GET /api/notifications`

이유:

- `notifications`, `rooms`, `members(actor)` 조인이 필요하다.
- 목록 응답은 entity 전체가 아니라 view model projection이 적합하다.
- 최신순 정렬, paging, receiver 제한 조건을 한 쿼리에서 명확히 표현할 수 있다.

권장 조건:

```text
notifications.receiver_member_id = :memberId
order by notifications.occurred_at desc, notifications.id desc
```

권장 join:

- `notifications.room_id = rooms.id`
- `notifications.actor_member_id = members.id`는 left join

### JPA Entity 사용

단건 상태 변경은 JPA entity 조회 후 도메인 메서드로 처리한다.

적용 대상:

- `POST /api/notifications/{notificationId}/read`

기준:

- `notificationId`와 `receiverMemberId`를 함께 조건으로 조회한다.
- 타인의 알림은 존재 여부를 노출하지 않기 위해 404로 처리하는 것을 우선한다.
- 이미 읽은 알림은 idempotent하게 200 OK와 `read=true`를 반환한다.
- `read_at`은 null일 때만 현재 시각으로 채운다.

## 6. Service Layer 기준

메인 서비스 레이어는 흐름이 보이게 오케스트레이션한다.

예시:

```kotlin
fun readNotification(memberId: Long, notificationId: Long): NotificationReadResponse {
    val member = currentMemberResolver.resolve(memberId)
    val notification = notificationReader.getOwnedNotification(notificationId, member.id)
    notification.markAsRead(clock.now())
    notificationWriter.save(notification)
    return NotificationReadResponse(read = true)
}
```

서비스가 호출하는 외부 책임 클래스의 공개 메서드에는 한국어 한 줄 주석을 둔다.

실패 로그는 언제/어디서/왜가 남게 한다.

```kotlin
logError(e) {
    "[알림 읽음 처리] 실패. " +
        "who=memberId:$memberId, " +
        "what=NotificationService.readNotification, " +
        "requestData=notificationId:$notificationId, " +
        "reason=${e.message}"
}
```

## 7. curl 테스트 계획

공통 전제:

```bash
BASE_URL=http://localhost:8080/api
```

검증은 Full Stack Dev Agent 구현 후 Tech Lead Agent가 curl로 1차 확인한다.

### 7-1. GET /api/notifications/latest

| 구분 | 케이스 | 명령 | 기대 결과 |
| --- | --- | --- | --- |
| Happy | 최신 알림 조회 | `curl -i -H "X-Member-Id: 1" "$BASE_URL/notifications/latest"` | HTTP 200, `items` 배열 반환 |
| Happy | 최신 알림 limit 3 검증 | `curl -s -H "X-Member-Id: 1" "$BASE_URL/notifications/latest"` | seed 알림이 4개 이상이어도 `items.length <= 3` |
| Happy | 최신순 정렬 | 위 응답의 `occurredAt` 확인 | `occurredAt desc`, 동률이면 `id desc` |
| Happy | 타입 구분 표시 | 위 응답의 `type` 확인 | `CHAT`, `LETTER`, `MEMORY`, `MISSION_APPROVAL_REQUEST`, `MISSION_APPROVAL_RATE` 중 하나 |
| Happy | target 이동 url shape 검증 | 위 응답의 `target.url` 확인 | `/rooms/{roomId}/...` 형태 |
| Edge | 알림이 없는 회원 | `curl -i -H "X-Member-Id: 3" "$BASE_URL/notifications/latest"` | HTTP 200, `items=[]` |
| Edge | `X-Member-Id` 누락 | `curl -i "$BASE_URL/notifications/latest"` | HTTP 401 또는 공통 인증 오류 |
| Edge | `X-Member-Id` 잘못된 형식 | `curl -i -H "X-Member-Id: abc" "$BASE_URL/notifications/latest"` | HTTP 400 |
| Edge | 존재하지 않는 회원 | `curl -i -H "X-Member-Id: 99999" "$BASE_URL/notifications/latest"` | HTTP 401 또는 404 계열 공통 오류 |

### 7-2. GET /api/notifications

| 구분 | 케이스 | 명령 | 기대 결과 |
| --- | --- | --- | --- |
| Happy | 전체 목록 기본 paging | `curl -i -H "X-Member-Id: 1" "$BASE_URL/notifications"` | HTTP 200, `page=0`, 기본 `size` 적용 |
| Happy | 전체 목록 paging 검증 | `curl -i -H "X-Member-Id: 1" "$BASE_URL/notifications?page=0&size=2"` | HTTP 200, `items.length <= 2` |
| Happy | 다음 page 조회 | `curl -i -H "X-Member-Id: 1" "$BASE_URL/notifications?page=1&size=2"` | HTTP 200, page 1 반환 |
| Happy | hasNext 검증 | size보다 알림이 많도록 seed 후 조회 | 다음 page가 있으면 `hasNext=true` |
| Happy | target 이동 url shape 검증 | 목록 응답의 각 `target.url` 확인 | type별 URL shape 일치 |
| Edge | 음수 page | `curl -i -H "X-Member-Id: 1" "$BASE_URL/notifications?page=-1&size=20"` | HTTP 400 |
| Edge | size 0 | `curl -i -H "X-Member-Id: 1" "$BASE_URL/notifications?page=0&size=0"` | HTTP 400 |
| Edge | size 상한 초과 | `curl -i -H "X-Member-Id: 1" "$BASE_URL/notifications?page=0&size=101"` | HTTP 400 |
| Edge | `X-Member-Id` 누락 | `curl -i "$BASE_URL/notifications"` | HTTP 401 또는 공통 인증 오류 |
| Edge | `X-Member-Id` 잘못된 형식 | `curl -i -H "X-Member-Id: abc" "$BASE_URL/notifications"` | HTTP 400 |

### 7-3. POST /api/notifications/{notificationId}/read

| 구분 | 케이스 | 명령 | 기대 결과 |
| --- | --- | --- | --- |
| Happy | read 처리 성공 | `curl -i -X POST -H "X-Member-Id: 1" "$BASE_URL/notifications/1/read"` | HTTP 200, `read=true` |
| Happy | idempotent read | 같은 명령 재호출 | HTTP 200, `read=true`, 서버 오류 없음 |
| Happy | read 후 목록 반영 | read 호출 후 latest/list 재조회 | 해당 알림 `read=true` |
| Edge | 존재하지 않는 notification id | `curl -i -X POST -H "X-Member-Id: 1" "$BASE_URL/notifications/99999/read"` | HTTP 404 |
| Edge | 타인의 notification read 차단 | `curl -i -X POST -H "X-Member-Id: 2" "$BASE_URL/notifications/1/read"` | HTTP 404 우선, 또는 403으로 통일 |
| Edge | `X-Member-Id` 누락 | `curl -i -X POST "$BASE_URL/notifications/1/read"` | HTTP 401 또는 공통 인증 오류 |
| Edge | `X-Member-Id` 잘못된 형식 | `curl -i -X POST -H "X-Member-Id: abc" "$BASE_URL/notifications/1/read"` | HTTP 400 |
| Edge | id path 형식 오류 | `curl -i -X POST -H "X-Member-Id: 1" "$BASE_URL/notifications/abc/read"` | HTTP 400 |

## 8. 프론트 1차 확인 기준

| 화면/행동 | 검증 기준 |
| --- | --- |
| 메인 화면 진입 | 프로필 카드 우측에 최신 알림 카드가 표시된다. |
| 최신 알림 카드 | 최대 3개만 보인다. |
| 타입 구분 | 채팅/편지/추억/미션이 배지, 색상, 텍스트로 구분된다. |
| 빈 상태 | 알림이 없으면 빈 상태 안내가 나온다. |
| 전체 보기 | 메인 화면 위에 전체 알림 모달이 열린다. |
| 전체 알림 목록 | paging API 결과를 사용하고 읽음/안읽음 상태가 구분된다. |
| 알림 클릭 | read API 호출 후 해당 방을 선택하고 target type에 맞는 기능 화면으로 이동한다. |
| 삭제/접근 불가 target | 앱이 깨지지 않고 삭제 안내 또는 기본 기능 화면으로 fallback한다. |

## 10. 1차 판정

구현 가능하다.

주의:

- 알림 읽음 처리는 반드시 receiver member 기준으로 제한한다.
- `MISSION_APPROVAL_RATE`를 `MISSION_PROGRESS` 같은 임의 타입으로 바꾸지 않는다.
- 최신 알림 API와 전체 목록 API의 item shape를 동일하게 유지한다.
- target URL은 서버에서 만들되, 프론트는 `roomId`와 `target.type`만으로도 최소 이동이 가능해야 한다.
- 삭제된 target은 서버/프론트 모두 null-safe fallback을 가져야 한다.
